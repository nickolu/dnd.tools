# UX Principles — dnd.tools

This tool is built for Nick. It should model his needs, workflow, preferences, and opinions. When in doubt, ask him — not a design framework.

## 1. Never be in my way

Every moment spent thinking about the tool is a moment lost from the game.

- **One-tap actions over multi-step flows.** If something takes two taps, ask if it can take one.
- **No decisions under pressure.** Don't present two ways to do the same thing. Pick one and make it obvious.
- **Glanceable state.** HP, initiative, conditions — readable at a glance, no scrolling required.
- **Fat-finger safe.** Destructive actions need confirmation. Interactive elements need breathing room.
- **The tool should feel invisible.** Like an extension of the DM screen, not a separate app demanding attention.

## 2. Easy to leave, easy to return

The DM constantly jumps between tools — Notion, D&D Beyond, homebrew docs, this. Never punish leaving.

- **Persistent state across tabs.** Close a tab, reopen — land right back where you were.
- **Deep-linkable everything.** Every spell, monster, encounter, and view should have a URL you can bookmark, share, or paste into Notion.
- **No session dependency.** Don't rely on in-memory state that dies with the tab. If it matters, persist it.
- **Link out freely.** The DM's workflow spans many tools. Be a good citizen in that ecosystem, not a walled garden.

## 3. Think like a game master

Use the vocabulary, mental models, and workflows that DMs already know.

- **Use D&D language.** "Initiative," "AC," "CR," "concentration" — not software abstractions. The tool should speak the same language as the rulebook.
- **Familiar affordances.** A stat block should look like a stat block. An initiative tracker should feel like a turn order. Don't reinvent patterns the tabletop community already understands.
- **Match the DM's workflow, not a product manager's.** Features should map to things a DM actually does at the table or during prep, not to abstract "user stories."

## 4. Ready for prep, ready for improv

Two modes, both first-class: deliberate session prep and real-time improvisation.

- **Heavy prep.** Encounter builder, saved monster/spell lists, pre-built setups. Organize large amounts of content for the DM who plans every encounter.
- **Improv.** Quick search, instant stat blocks, one-click HP tracking. For the DM who needs a goblin stat block right now because the party went off-script.
- **Don't force one mode to use the other.** A quick lookup shouldn't navigate past encounter-builder UI. Building encounters shouldn't require re-searching for monsters you already found.

## 5. Laptop-first, mobile-ready

Primary use is on a laptop during a game session. Mobile is for quick reference and brainstorming between sessions.

- **Design for laptop first.** Then ensure mobile is usable for search, lookup, and light tasks.
- **Mobile doesn't need full feature parity.** Encounter management on a phone is a stretch — optimize mobile for reference.
- **No horizontal scroll on any viewport.**

## 6. Nick's tool, Nick's opinions

This isn't a product for a market. It's a personal tool. Optimize for one user.

- **Ask Nick, not best practices.** When a design decision is ambiguous, the answer is whatever Nick prefers — not what a UX textbook says.
- **Ship fast, refine later.** Get it working, get it in front of Nick, iterate based on real use. Don't polish hypotheticals.
- **Opinionated defaults.** Pick the option Nick would pick. Don't add settings for things that have an obvious right answer for his workflow.
